# ЛР №10 — усі 45 відповідей: Maven, JDBC, SQL і транзакції

[Почати з пояснення всього проєкту](DEFENSE.md) · [Відповіді до Hibernate](QA-LR11.md)

Нумерація й формулювання відповідають контрольним питанням з умови. Виділену коротку відповідь можна сказати викладачу; пояснення й приклади потрібні, щоб відповідати на уточнення. Приклади коду скорочені для навчання; готові реалізації знаходяться у вказаних класах.

## Maven і керування залежностями

### 1. Яку проблему вирішує Maven порівняно з ручним підключенням .jar-файлів у classpath? Що саме ви перестали робити вручну?

**Для захисту:** Maven автоматизує збирання проєкту й отримання бібліотек за описом у `pom.xml`. Я перестав вручну завантажувати кожен JAR, шукати його залежності й формувати classpath для компіляції, тестів та запуску.

**Визначення:** JAR — архів із Java-класами й ресурсами; classpath — перелік місць, де Java шукає класи. POM — опис проєкту, залежностей і плагінів збирання.

Достатньо вказати H2 у залежностях, і Maven завантажить драйвер у локальний кеш `~/.m2/repository`. Версії та плагіни фіксуються в репозиторії, тому інший комп'ютер може відтворити збирання. Перший запуск потребує доступу до репозиторію залежностей; кеш дозволяє повторно використовувати вже отримані файли.

**Запам'ятай:** `pom.xml` — рецепт, Maven — виконавець рецепта.

### 2. Що таке GAV-координати (groupId, artifactId, version)? За якими координатами Maven знайшов ваш JDBC-драйвер?

**Для захисту:** GAV — три значення, які ідентифікують артефакт: група, назва й версія. Драйвер у мене — `com.h2database:h2:2.3.232`.

```xml
<dependency>
    <groupId>com.h2database</groupId>
    <artifactId>h2</artifactId>
    <version>2.3.232</version>
    <scope>runtime</scope>
</dependency>
```

`groupId` зазвичай позначає організацію/простір імен; `artifactId` — конкретну бібліотеку; `version` — її випуск. Сам проєкт має координати `com.eugene:personal-notes:1.0.0`. Назва Java-пакета й groupId пов'язані домовленістю, але Maven не вимагає їхньої повної тотожності.

### 3. Що таке транзитивні залежності? Покажіть, як їх побачити (mvn dependency:tree) і наведіть приклад зі свого проєкту.

**Для захисту:** Транзитивна залежність — бібліотека, потрібна іншій моїй залежності. Maven отримує її автоматично. Дерево показує `mvn dependency:tree`.

```powershell
.\mvnw.cmd dependency:tree
```

У гілці ЛР №10: `HikariCP:6.3.0 → slf4j-api:1.7.36`. У спільній гілці ЛР №11 Hibernate також підтягує `jakarta.persistence-api:3.2.0`; SLF4J API явно узгоджений із версією simple `2.0.20`. Це різні зафіксовані стани проєкту, тому дерево у двох гілках відрізняється.

Якщо різні бібліотеки вимагають різні версії тієї самої залежності, Maven застосовує правила вибору версії; явна залежність або dependencyManagement дає змогу керувати результатом. [Механізм залежностей Maven](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html).

### 4. Що означає <scope> у залежності (compile, runtime, test)? Чому JDBC-драйвер зазвичай має scope runtime, а JUnit test?

**Для захисту:** Scope визначає, на яких етапах потрібна залежність.

| Scope | Компіляція основного коду | Запуск застосунку | Тести |
| --- | --- | --- | --- |
| `compile` — типовий | так | так | так |
| `runtime` | ні | так | так |
| `test` | ні | ні як залежність застосунку | так |

H2 потрібна під час запуску для JDBC-підключення. Основний код використовує стандартні `java.sql`/`javax.sql`, а не імпорти H2, тому драйверу достатньо runtime. HikariCP має compile, бо код прямо імпортує його класи. JUnit використовується лише у `src/test/java`, тому має test.

Scope не означає, що JAR автоматично вбудовується в наш звичайний JAR: за залежностями під час запуску тут стежить Maven exec plugin. [Офіційні scopes Maven](https://maven.apache.org/guides/introduction/introduction-to-dependency-mechanism.html#dependency-scope).

### 5. Опишіть, що робить Maven при виконанні mvn package: які фази життєвого циклу проходять до цього моменту?

**Для захисту:** Виконує фази default lifecycle від початку до package: перевіряє опис, обробляє ресурси, компілює основний код і тести, запускає тести та пакує результат.

Навчальна схема: `validate → compile → test → package`. Між ними також є `initialize`, фази генерації/обробки джерел і ресурсів, `test-compile`, `prepare-package`. Не кожна фаза має роботу: виконуються прив'язані до неї plugin goals.

Результат нашого JAR-проєкту: `target/personal-notes-1.0.0.jar`. Ресурси також потрапляють до збірки. `package` сам собою не означає `clean` і не виконує фазу `verify`, розташовану пізніше. `exec:java` — goal плагіна; він не компілює нові джерела автоматично, тому спочатку потрібен compile. [Життєвий цикл Maven](https://maven.apache.org/guides/introduction/introduction-to-the-lifecycle).

### 6. Чим відрізняються mvn install і mvn package? Куди потрапляє результат кожної з команд?

**Для захисту:** `package` створює артефакт у `target/`, а `install` проходить далі й додає артефакт та його POM до локального Maven-репозиторію.

Після package є `target/personal-notes-1.0.0.jar`. Після install він також доступний за GAV у `~/.m2/repository/com/eugene/personal-notes/1.0.0/`, щоб інші локальні Maven-проєкти могли оголосити його залежністю. Install не означає публікацію на GitHub чи на віддалений Maven-сервер; для віддаленого репозиторію існує deploy.

### 7. Для чого в pom.xml потрібні властивості на кшталт maven.compiler.release і project.build.sourceEncoding? Що може піти не так без них, зокрема з кирилицею?

**Для захисту:** Release фіксує цільову версію Java й доступні API, а sourceEncoding задає, як читати текст джерел. У мене Java 25 та UTF-8.

```xml
<maven.compiler.release>25</maven.compiler.release>
<project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
```

Без правильної версії можна отримати несумісний bytecode або виклик API, відсутнього на цільовій Java. Без узгодженого кодування кирилиця може перетворитися на неправильні символи чи спричинити помилки компіляції. Кодування компілятора й термінала — окремі питання: `.mvn/jvm.config` додатково задає UTF-8 для JVM та виведення. Потрібна повна JDK 25+, а не лише JRE.

### 8. Чому каталог target/ не потрапляє в репозиторій? Що з ним станеться після mvn clean?

**Для захисту:** Target містить відтворювані результати збирання: класи, JAR, скопійовані ресурси та звіти тестів. Їх можна отримати з джерел, тому каталог виключено через `.gitignore`.

`mvn clean` видаляє target за типовими налаштуваннями clean plugin. Наступне збирання створює його заново. Файлова БД зберігається в `data/`, тому clean не видаляє нотатки. Gitignore запобігає додаванню нових файлів; він сам по собі не прибирає вже відстежувані файли з історії.

## Основи JDBC

### 9. Опишіть послідовність дій при читанні даних через JDBC: від отримання з'єднання до закриття ресурсів.

**Для захисту:** Позичаю Connection у DataSource, готую PreparedStatement, задаю параметри, виконую executeQuery, обходжу ResultSet через next, перетворюю рядки на об'єкти й закриваю ресурси.

```java
try (Connection connection = dataSource.getConnection();
     PreparedStatement statement = connection.prepareStatement(
             "SELECT id, name FROM categories WHERE id = ?")) {
    statement.setLong(1, id);
    try (ResultSet rows = statement.executeQuery()) {
        if (rows.next()) {
            return new Category(rows.getLong("id"), rows.getString("name"));
        }
    }
}
throw new EntityNotFoundException(id);
```

У нас цей каркас узагальнено в `AbstractJdbcCrudService.query` і `findById`. Після завершення ResultSet закривається першим, statement другим, connection останнім; для Hikari close повертає з'єднання до пулу.

### 10. Для чого потрібен JDBC-драйвер? Чому код працює через інтерфейси Connection, Statement, ResultSet, а не через класи конкретної СУБД? Який принцип проєктування тут працює?

**Для захисту:** Драйвер реалізує JDBC для конкретної СУБД. Наш код залежить від стандартних інтерфейсів, а драйвер перетворює виклики на роботу з H2.

Це програмування до інтерфейсів та зменшення залежності від конкретної реалізації. Змінити драйвер і URL легше, ніж переписувати всі виклики. Але повної переносимості це не гарантує: H2 `MERGE ... KEY(id)`, SQL-типи й поведінка блокувань можуть вимагати змін при переході на PostgreSQL/MySQL. Hibernate також зрештою використовує JDBC-драйвер.

### 11. Що містить JDBC URL? Розберіть свій URL по частинах.

**Для захисту:** URL указує драйверу, до якої БД і яким способом підключатися. У мене `jdbc:h2:file:./data/notes`.

`jdbc` — формат JDBC URL; `h2` — тип драйвера; `file` — файловий режим; `./data/notes` — шлях від поточного робочого каталогу без розширення. H2 створює `notes.mv.db`. Тут немає хоста й порту, бо H2 працює вбудовано в процесі Java. Для серверної PostgreSQL URL виглядав би, наприклад, `jdbc:postgresql://localhost:5432/notes`. Логін і пароль у нас передаються окремими налаштуваннями.

### 12. Чому Connection, Statement і ResultSet потрібно закривати? Що дає try-with-resources порівняно з finally?

**Для захисту:** Це ресурси БД, а не просто об'єкти в пам'яті. Незакриті об'єкти можуть утримувати з'єднання, курсори та інші ресурси; пул зрештою може вичерпатися.

Try-with-resources автоматично викликає close навіть при винятку, закриває кілька ресурсів у зворотному порядку та зберігає помилки закриття як suppressed, якщо вже є основна помилка. У finally це довелося б акуратно писати вручну. Garbage Collector не є заміною своєчасному close.

**Важлива деталь:** `connection.close()` у пулі повертає позичене з'єднання. `dataSource.close()` у Hikari завершує сам пул. Це різні рівні життєвого циклу.

### 13. Чим відрізняються executeQuery, executeUpdate і execute? Що повертає кожен із них?

**Для захисту:** `executeQuery` повертає ResultSet, `executeUpdate` — кількість змінених рядків, `execute` — ознаку типу першого результату.

| Метод | Приклад | Результат |
| --- | --- | --- |
| `executeQuery()` | SELECT | `ResultSet` |
| `executeUpdate()` | INSERT/UPDATE/DELETE | `int`, кількість змін; для DDL зазвичай 0 |
| `execute()` | універсальні команди | true, якщо перший результат — ResultSet; інакше false |

False від execute **не означає помилку SQL**. Далі читають `getUpdateCount()` або `getResultSet()`; для кількох результатів є `getMoreResults()`. У проєкті query застосовується для читання, update — для CRUD, execute — для init.sql.

### 14. Як працює ResultSet.next()? Де знаходиться курсор одразу після виконання запиту?

**Для захисту:** Спочатку курсор стоїть перед першим рядком. Next пересуває його на наступний рядок і повертає true, якщо рядок існує.

```java
while (rows.next()) {
    System.out.println(rows.getString("name"));
}
```

Для порожнього результату перший next одразу дає false. Не можна читати поля поточного рядка до успішного next. Для одного можливого запису вистачає if, для списку потрібен while. Наш `query` на кожному рядку викликає mapRow. [Java ResultSet API](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/ResultSet.html).

### 15. Що станеться, якщо в ResultSet читати колонку, що містить NULL, методом getInt? Як відрізнити 0 від NULL (wasNull, getObject)?

**Для захисту:** GetInt повертає 0 і для SQL NULL, і для справжнього нуля. Відразу після читання треба перевірити wasNull або читати nullable wrapper.

```java
int value = rows.getInt("optional_number");
Integer number = rows.wasNull() ? null : value;
// Альтернатива за підтримки драйвером:
Integer other = rows.getObject("optional_number", Integer.class);
```

WasNull стосується **останнього прочитаного значення**, тому між getter та перевіркою не слід читати іншу колонку. Примітив int не може містити null, Integer може. У таблицях нашого проєкту основні поля NOT NULL, але принцип важливо знати для необов'язкових полів.

### 16. Як отримати згенерований базою id після INSERT (RETURN_GENERATED_KEYS)? Навіщо це потрібно в save?

**Для захисту:** Під час підготовки INSERT прошу драйвер повернути ключі, після виконання читаю getGeneratedKeys. Це потрібно, щоб об'єкт/клієнт знав id нового запису, призначений БД.

```java
try (PreparedStatement statement = connection.prepareStatement(
        "INSERT INTO example(name) VALUES (?)", Statement.RETURN_GENERATED_KEYS)) {
    statement.setString(1, name);
    statement.executeUpdate();
    try (ResultSet keys = statement.getGeneratedKeys()) {
        if (keys.next()) {
            long generatedId = keys.getLong(1);
        }
    }
}
```

Це **навчальний приклад для таблиці з DB-generated ключем**, не наш фактичний save. У ЛР №10 id уже призначає доменний BaseEntity, його поле незмінне, а save повертає void. Тому наш INSERT/MERGE отримує id параметром і не використовує RETURN_GENERATED_KEYS. Не кажи на захисті, що H2 сама генерує наші JDBC-id. [Statement API](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/Statement.html).

## PreparedStatement

### 17. Чим PreparedStatement відрізняється від Statement? Назвіть щонайменше дві переваги.

**Для захисту:** PreparedStatement відокремлює SQL-шаблон від значень, дає типізовані параметри та повторне використання одного запиту, зокрема для batch.

```java
PreparedStatement statement = connection.prepareStatement(
        "SELECT * FROM notes WHERE name = ?");
statement.setString(1, "План");
```

Переваги: параметризовані значення не змінюють структуру SQL; драйвер обробляє перетворення типів, лапки й дати; можна багато разів задавати нові значення. Повторне використання підготовки/плану може покращити продуктивність, але конкретна серверна підготовка й кешування залежать від драйвера та СУБД. Сам клас не захистить, якщо перед prepareStatement уже склеїти небезпечний текст.

### 18. Що таке SQL-ін'єкція? Покажіть на прикладі, як злам працює при склеюванні рядків.

**Для захисту:** SQL-ін'єкція — ситуація, коли введені дані стають частиною команди й змінюють її сенс.

```java
// Поганий приклад лише для пояснення:
String sql = "SELECT * FROM notes WHERE name = '" + input + "'";
```

Для `input = "' OR '1'='1' --"` виходить:

```sql
SELECT * FROM notes WHERE name = '' OR '1'='1' --'
```

Умова `'1'='1'` істинна, а решта після `--` — коментар; запит може повернути всі рядки. У виконуваному коді такого методу немає: він показаний у README. Параметризований `JdbcNoteService.findByName` із тим самим рядком шукає буквальну назву, а не виконує OR.

### 19. Чому PreparedStatement захищає від SQL-ін'єкції? Чи можна захиститися ручним екрануванням лапок і чому цього недостатньо?

**Для захисту:** Структура запиту задана наперед, а значення передаються як параметри. Лапки, OR та коментар усередині значення лишаються даними.

```java
statement.setString(1, "' OR '1'='1' --");
```

Ручне екранування легко зробити неповним: правила залежать від контексту, діалекту, кодування та типу значення. Параметри надійніше для даних. Але для динамічних ідентифікаторів потрібен окремий whitelist. У тесті `preparedStatementTreatsInjectionAsLiteralData` перевіряється і відсутність зайвих збігів, і коректний пошук нотатки, назва якої буквально дорівнює payload.

**Запам'ятай:** SQL — інструкція, параметр — вміст клітинки.

### 20. Чи можна параметризувати через ? назву таблиці або напрямок сортування (ORDER BY ?)? Як безпечно реалізувати вибір поля сортування?

**Для захисту:** Параметр підставляє значення, а не назву таблиці/колонки чи ключове слово ASC/DESC. Для структури запиту потрібен whitelist дозволених варіантів.

```java
String order = switch (sortOption) {
    case "name" -> "name ASC, id ASC";
    case "priority" -> "priority ASC, id ASC";
    default -> throw new IllegalArgumentException("Unknown sort");
};
```

Потім до SQL можна додати саме цей контрольований літерал, а не довільне введення. `ORDER BY ?` зі значенням `"name"` може сортувати за константою або бути відхилений, але не вибирає колонку name. У нашому коді порядок сортування — фіксовані SQL-шаблони розробника.

### 21. Чому пароль до БД не можна зберігати в коді та комітити в репозиторій? Як це організовано у вашому проєкті?

**Для захисту:** Пароль у коді або історії Git може отримати кожен, хто має доступ до репозиторію. Видалення з останнього коміту не видаляє його з історії.

Наші URL/user/password читаються з application.properties; `NOTES_DB_URL`, `NOTES_DB_USER`, `NOTES_DB_PASSWORD` мають пріоритет. У репозиторії лише параметри локальної навчальної H2 з порожнім паролем, справжні реквізити передаються через оточення.

```powershell
$env:NOTES_DB_PASSWORD = 'my-local-secret'
```

Перенесення справжнього пароля з Java в properties, якщо properties теж закомічений, саме по собі не робить його секретом. У production застосовують секрети середовища/сховище секретів і контроль доступу.

## Проєктування БД

### 22. Навіщо в таблиці первинний ключ? Який ключ ви вибрали (природний чи сурогатний) і чому?

**Для захисту:** Первинний ключ однозначно ідентифікує рядок і не допускає дубля та NULL. Я вибрав сурогатний додатний BIGINT id для обох таблиць.

Природний ключ має предметний зміст, наприклад унікальний номер документа. Сурогатний — технічний ідентифікатор. Назва нотатки може повторюватися й змінюватися, тому вона погано підходить для PK. Унікальність імені категорії задано окремим UNIQUE. Не плутай «сурогатний» з «автоматично генерується БД»: у нас він технічний, але призначається Java-кодом.

### 23. Для чого потрібні обмеження NOT NULL, UNIQUE, CHECK? Наведіть по одному прикладу зі своєї схеми.

**Для захисту:** NOT NULL вимагає значення; UNIQUE забороняє повтори; CHECK перевіряє умову для рядка.

```sql
name VARCHAR(255) NOT NULL UNIQUE,
priority INTEGER NOT NULL CHECK (priority BETWEEN 1 AND 5)
```

У categories.name є NOT NULL, UNIQUE та CHECK непорожньої назви після TRIM. У notes.priority — діапазон 1..5. Інший CHECK узгоджує note_type з reminder_hours/repeat_hours. У SQL CHECK сам по собі зазвичай не забороняє NULL, бо невідомий результат не тотожний false, тому обов'язковим полям додано окремий NOT NULL.

Ці правила діють і при записі через JDBC, і через ORM, і через сторонню SQL-консоль.

### 24. Чому для грошових сум використовують NUMERIC/DECIMAL, а не FLOAT/DOUBLE? Як тип відображається на Java (BigDecimal)?

**Для захисту:** Гроші потребують точної десяткової арифметики, а binary float/double не представляють багато десяткових дробів точно. Тому БД — NUMERIC/DECIMAL, Java — BigDecimal.

```java
BigDecimal price = new BigDecimal("19.90");
statement.setBigDecimal(1, price);
```

`NUMERIC(10,2)` означає до 10 десяткових цифр загалом, із них 2 після крапки. Для BigDecimal краще рядковий конструктор або valueOf, а не `new BigDecimal(0.1)`, який переносить похибку double. При діленні задають правила округлення.

У наших нотатках грошей **немає**. DOUBLE PRECISION використаний для приблизної тривалості в годинах відповідно до успадкованого API double, а не для ціни.

### 25. Що таке зовнішній ключ і яку цілісність він гарантує? Що станеться при видаленні батьківського запису залежно від ON DELETE RESTRICT / CASCADE / SET NULL?

**Для захисту:** FK гарантує, що посилання дитини веде на наявного батька. У нас `notes.category_id → categories.id`.

| Дія | Видалення категорії з нотатками |
| --- | --- |
| RESTRICT | забороняється |
| CASCADE | БД видаляє також пов'язані нотатки |
| SET NULL | БД очищає category_id; колонка повинна дозволяти NULL |

Обрано **RESTRICT**, щоб випадкове видалення категорії не знищило нотатки. Для видалення спочатку переношу дітей або явно видаляю їх. У нашому DDL category_id NOT NULL, тому просте перемикання на SET NULL без зміни моделі суперечило б обмеженню.

### 26. Що означає, що init.sql ідемпотентний? Як це досягається і чому це важливо при повторному запуску?

**Для захисту:** Повторне виконання скрипту дає той самий потрібний стан без дублювання й помилок через уже створені об'єкти. Ми застосували CREATE TABLE/INDEX IF NOT EXISTS і не додаємо повторні seed-дані.

```sql
CREATE TABLE IF NOT EXISTS categories (...);
CREATE INDEX IF NOT EXISTS idx_notes_category ON notes(category_id);
```

Тому програму можна запускати багато разів зі збереженими нотатками. Однак IF NOT EXISTS **не виправляє** структуру старої таблиці: додавання колонки в текст скрипту не змінить уже наявну таблицю. Для розвитку реальної схеми потрібні міграції, наприклад Flyway/Liquibase; у ЛР №11 Hibernate validate має виявляти частину несумісностей.

### 27. Чому init.sql лежить у src/main/resources? Як програма знаходить і читає цей файл із classpath?

**Для захисту:** Resources — стандартний каталог файлів, потрібних під час запуску. Maven копіює їх у target/classes і включає в JAR; завантажувач класів знаходить їх незалежно від місця запуску.

```java
InputStream input = DBConnection.class.getClassLoader()
        .getResourceAsStream("init.sql");
```

Це читання ресурсу, а не жорстко заданого шляху `src/main/resources/init.sql`. Після пакування каталог src може взагалі бути відсутнім. DBConnection читає текст UTF-8 і виконує DDL через PreparedStatement. Наш простий поділ за `;` розрахований саме на поточний скрипт без крапок із комою всередині рядків/процедур; це не універсальний SQL-парсер.

### 28. Для чого потрібен індекс? Які операції він прискорює, а які сповільнює? Чи є у вашій схемі стовпці, для яких він доречний?

**Для захисту:** Індекс — додаткова структура пошуку, яка може зменшити читання таблиці при WHERE/JOIN/ORDER BY. Його потрібно підтримувати при INSERT/UPDATE/DELETE, тому запис стає дорожчим.

У нас `idx_notes_category(category_id)` допомагає знаходити дітей категорії та переносити їх; `idx_notes_name_priority(name, priority, id)` відповідає сортуванню. Складений індекс особливо корисний за його лівим префіксом: цей індекс не рівнозначний окремому індексу лише priority. PK та UNIQUE також зазвичай підтримуються індексами.

Індекс не гарантує прискорення будь-якого запиту: оптимізатор може вибрати повний перегляд, наприклад для малої таблиці або великої частки рядків. Перевіряють план виконання, а не лише факт існування індексу.

## Singleton і архітектура

### 29. Що таке патерн Singleton і яку задачу він розв'язує? Як у вашому DBConnection гарантовано, що екземпляр один?

**Для захисту:** Singleton дає єдиний екземпляр сервісу з контрольованим доступом у межах відповідного завантажувача класів JVM. У DBConnection приватний конструктор і статичний вкладений Holder.

```java
private static final class Holder {
    private static final DBConnection INSTANCE = new DBConnection();
}
public static DBConnection getInstance() { return Holder.INSTANCE; }
```

Саме Holder створює один об'єкт при першому зверненні. Він володіє **пулом HikariDataSource**, а не єдиним Connection. Не слід заявляти, що Singleton забезпечує один об'єкт на всі комп'ютери або всі запущені процеси: кожна JVM має своє середовище.

### 30. Чим відрізняється ліниве створення від раннього? Чи є ваша реалізація потокобезпечною і як ви це перевіряли?

**Для захисту:** Раннє створення відбувається під час ініціалізації класу, ліниве — лише коли екземпляр уперше потрібен. Holder дає ліниве потокобезпечне створення завдяки гарантіям ініціалізації класів JVM.

Кілька потоків не зможуть незалежно виконати статичну ініціалізацію Holder й отримати різні INSTANCE. Наші інтеграційні тести перевіряють роботу DataSource та життєвий цикл, але **окремого stress-тесту одночасного getInstance у наборі немає**. Потокобезпечність створення обґрунтовується конструкцією й гарантією JVM; не потрібно вигадувати експеримент, якого не було.

Потокобезпечність Singleton не означає, що всі бізнес-операції автоматично вільні від конфліктів. Наприклад, паралельне створення категорії з однаковою назвою може завершитися UNIQUE-помилкою.

### 31. Які недоліки у Singleton (прихована залежність, складність тестування, глобальний стан)? Чи є вони у вашому проєкті?

**Для захисту:** Глобальний getInstance приховує залежність, ускладнює підміну для тестів і прив'язує код до спільного життєвого циклу. Після close наш Singleton не створюється заново.

Для зменшення цих проблем JDBC-сервіси мають конструктор із DataSource, а Hibernate-сервіси — із JpaUtil. Тести передають власну ізольовану БД замість production Singleton. У застосунку все одно є глобальна точка доступу, тому недоліки повністю не зникають. Ресурси завершує точка запуску, а не довільний сервіс посеред операції.

### 32. Чому один спільний Connection на весь застосунок може бути проблемою? Що стається з ним при багатопотоковості та при обриві зв'язку?

**Для захисту:** Connection має стан сесії й транзакції. Якщо клієнти ділять один об'єкт, зміни autoCommit, commit, rollback або close одного клієнта впливають на інших.

Наприклад, потік A почав перенесення нотаток, а потік B зробив commit на тому самому Connection — межі операцій змішуються. Обрив робить спільне з'єднання непридатним для всіх. У нас кожна операція позичає Connection із пулу; багатокрокова транзакція тримає один позичений Connection до кінця.

**Важливе уточнення:** Пул може замінити зламане з'єднання для наступних операцій, але не відновлює автоматично вже обірвану транзакцію без втрати її контексту.

### 33. Що таке пул з'єднань? Навіщо він потрібен, якщо відкривати нове з'єднання дорого?

**Для захисту:** Пул утримує набір готових з'єднань і видає їх на час роботи. Close повертає позичене з'єднання, тож не потрібно створювати нове фізичне підключення для кожного запиту.

Створення з'єднання може включати мережу, автентифікацію, створення серверної сесії. Пул також обмежує кількість одночасних підключень. Наш HikariCP налаштований на максимум 4, мінімум idle 1. Якщо всі зайняті, новий запит чекає до налаштованого таймауту; пул не є безмежним прискорювачем. Для вбудованої H2 мережевої вартості немає, але керування ресурсами й життєвим циклом залишається корисним.

### 34. Що змінилося в коді, який користується сервісом, коли ви замінили реалізацію в пам'яті на JDBC-реалізацію? Який принцип проєктування це демонструє?

**Для захисту:** Змінився вибір реалізації в точці створення сервісу та керування ресурсами/початковим читанням. Виклики CRUD у сценаріях меню залишились тими самими.

```java
NoteService service = new JdbcNoteService();
service.save(note);
Note loaded = service.findById(note.getId());
```

У спільній гілці NoteServices вибирає memory/jdbc/hibernate. Це залежність клієнта від абстракції та взаємозамінність реалізацій за збереженого контракту. Поведінка зберігання відрізняється: пам'ять зникає після виходу, БД зберігається. Не треба казати, що не змінився взагалі жоден рядок Main: композиція й закриття ресурсів справді були адаптовані.

### 35. Чому JdbcProductService має реалізовувати той самий інтерфейс ProductService, що й версія з ЛР №7? Що було б, якби ви створили новий окремий клас з іншими методами?

**Для захисту:** У моїй предметній області це NoteService. Однаковий інтерфейс дозволяє замінити сховище, зберігши код клієнта й семантику операцій.

`InMemoryNoteService`, `JdbcNoteService`, `HibernateNoteService` усі надають save/findById/delete та сортування. Окремий клас з іншим API змусив би меню знати конкретне сховище, робити умовні гілки або мати дубльовані сценарії. Саме імплементація інтерфейсу не гарантує сумісності: потрібно також дотримуватися поведінки, наприклад `delete` повертає false для відсутнього id, а findById кидає власний виняток.

### 36. Де в коді проходить межа між «роботою з БД» і «логікою застосунку»? Чи є у вас SQL поза JDBC-сервісами?

**Для захисту:** Меню викликає сервіси й не будує SQL. Основні CRUD-запити та транзакція перенесення знаходяться в JDBC-сервісах, робота з підключенням — у db-пакеті.

Не можна буквально стверджувати, що SQL немає ніде поза сервісами: `DBConnection` виконує init.sql і читає MAX(id), `BatchBenchmark` очищає свою тестову таблицю, а тести мають SQL для перевірки обмежень. Це інфраструктура й перевірки, а не SQL у користувацькому меню. В ORM-сервісах використовується JPQL, а Hibernate генерує SQL. Межа корисна тим, що UI не залежить від назв колонок і способу підключення.

## Транзакції

### 37. Що таке транзакція? Поясніть властивості ACID на прикладі вашої операції, що змінює кілька таблиць.

**Для захисту:** Транзакція об'єднує кілька дій в одну одиницю підтвердження. У мене це перенесення нотаток, видалення старої категорії та перейменування цільової.

| Властивість | Зміст у нашому прикладі |
| --- | --- |
| Atomicity, атомарність | або виконані всі три зміни, або жодна |
| Consistency, узгодженість | зберігаються FK/UNIQUE/CHECK та інваріанти операції |
| Isolation, ізоляція | паралельні операції взаємодіють за рівнем ізоляції й блокуваннями; категорії блокуємо FOR UPDATE |
| Durability, довговічність | підтверджені дані зберігаються за гарантіями налаштованої БД/ОС/диска |

Ізоляція не означає автоматично SERIALIZABLE: у нас рівень спеціально не підвищується. У H2 також є налаштування відкладеного запису; не обіцяй абсолютного захисту від будь-якого фізичного збою без аналізу цих налаштувань.

### 38. Що робить setAutoCommit(false) і що відбувається, якщо після нього забути викликати commit()?

**Для захисту:** Він вимикає автоматичне підтвердження кожної команди. Наступні команди належать транзакції, яку треба явно завершити commit або rollback.

Без commit зміни не можна вважати підтвердженими. Відкрита транзакція може утримувати блокування. У нашому пулі незавершена робота відкочується/стан скидається при поверненні з'єднання, але переносимий JDBC-код повинен сам явно завершувати транзакцію. Close для звичайного Connection з активною транзакцією має залежну від реалізації поведінку; на автоматичний commit покладатися не можна. [Контракт Connection](https://docs.oracle.com/en/java/javase/25/docs/api/java.sql/java/sql/Connection.html).

**Запам'ятай:** `false → кілька дій → commit / rollback`.

### 39. У якому місці коду ви викликаєте rollback() і чому саме там? Що станеться з даними при винятку без відкату?

**Для захисту:** У catch усередині JdbcTransaction.run, поки той самий Connection ще відкритий. Він охоплює SQL-операції та commit.

```java
connection.setAutoCommit(false);
try {
    work.execute(connection);
    connection.commit();
} catch (SQLException | RuntimeException failure) {
    connection.rollback();
    throw failure;
}
```

У повній реалізації помилка rollback додається як suppressed, щоб не загубити початкову причину. Java-виняток сам по собі не гарантує відкат усіх попередніх SQL-команд: стан транзакції залежить від СУБД і типу помилки. Без явного завершення залишаються ризики незавершеної роботи, блокувань або помилкового подальшого commit.

У демо UNIQUE-помилка на перейменуванні виникає **після** перенесення notes і DELETE categories; rollback повертає обидві таблиці до попереднього стану.

### 40. Чому в ORDER BY на стороні БД сортувати вигідніше, ніж завантажити всі записи й відсортувати Comparator-ом? Коли різниця стає помітною?

**Для захисту:** БД може використати індекс і віддати тільки потрібну відсортовану сторінку. Java-сортування спочатку вимагає завантажити й створити всі об'єкти, потім витрачає додаткові CPU та пам'ять.

```sql
ORDER BY name, priority, id
LIMIT ? OFFSET ?
```

Перевага особливо важлива для великих таблиць і коли потрібні лише перші 20 рядків. Якщо все одно читаємо всі записи, виграш не гарантований: витрати й план залежать від запиту. Для довільного переданого Comparator наш сервіс залишає Java-сортування заради сумісності; фіксовані відомі сортування виконує SQL.

### 41. Яку роль у сортуванні грає порядок рядків без ORDER BY? Чи гарантований він?

**Для захисту:** Без ORDER BY порядок результату не гарантований. Навіть якщо сьогодні він збігається з id або порядком INSERT, на це не можна покладатися.

Він може змінитися через індекс, план запиту, оновлення чи версію БД. Тому наш findAll явно використовує `ORDER BY id`, а сортування за назвою має додатковий id. Лише `ORDER BY name` також не визначає взаємний порядок різних нотаток з однаковою назвою. Для стабільної пагінації потрібен однозначний порядок, наприклад `(name, id)`.

### 42. Чому findAll() без обмежень небезпечний для великої таблиці? Як працює пагінація через LIMIT/OFFSET і які в неї обмеження?

**Для захисту:** FindAll завантажує весь набір у пам'ять і може спричинити довге очікування чи OutOfMemoryError. Пагінація обмежує кількість отриманих рядків.

`LIMIT 20 OFFSET 40` означає пропустити 40 рядків визначеного порядку й узяти наступні максимум 20 — третю сторінку за нумерації від першої. У нашому findPage limit 1..1000, offset невід'ємний, порядок name/id.

Великий OFFSET дорогий: БД усе одно має дістатися до пропущених рядків. При змінах між окремими запитами можливі повтори/пропуски. Альтернатива — keyset-пагінація після останньої пари `(name, id)`. Попереднє меню все ще читає повний знімок для малих навчальних даних; наявність findPage не означає, що меню вже перероблено на сторінки.

### 43. Як працює addBatch/executeBatch і чому пакетна вставка швидша за вставку по одному запису? Які цифри ви отримали у своєму вимірюванні?

**Для захисту:** Для одного PreparedStatement задаю параметри, викликаю addBatch для кожного запису, потім executeBatch для групи. Менше повторної підготовки й викликів, а одна транзакція зменшує кількість commit.

У saveBatch блоки по **500**, але транзакція одна на **всю колекцію**; помилка в останньому блоці відкочує й перші блоки. Перед записом колекція копіюється й перевіряється на null. Використано MERGE; для нових id він вставляє рядки.

**Результат із ЛР №10:** 5000 категорій, H2 file, 3 повтори, прогрів 500, Windows/Temurin 25.0.5. Медіана save по одному — **197,88 мс**, batch — **101,61 мс**, співвідношення **1,95×**.

Це замір усього шляху: save має commit на запис, batch — один commit на всі записи. Не можна приписувати весь виграш лише addBatch; для вбудованої H2 немає мережевого round trip. Новий запуск може дати інші числа.

### 44. Як у AbstractJdbcCrudService реалізовано Template Method: який метод є каркасом, які методи перекриваються в підкласах?

**Для захисту:** Абстрактний клас фіксує послідовність JDBC-дій, а підкласи заповнюють змінні частини: SQL, параметри й перетворення рядка.

Каркаси: `query`, `save`, `findById`, `delete`, `saveBatch`. Наприклад save перевіряє аргумент → запускає транзакцію → викликає beforeSave → готує statement → setParameters → executeUpdate. Підкласи задають `selectSql`, `saveSql`, `deleteSql`, `mapRow`, `setParameters`; необов'язковий hook beforeSave у JdbcNoteService створює категорію.

`final` у публічних методах не дозволяє підкласам випадково обійти каркас. `T extends BaseEntity` дозволяє спільному коду отримувати id/name незалежно від конкретного типу. JdbcCategoryService використовує той самий механізм для другої сутності.

### 45. Що саме ви тестуєте на H2 in-memory і чим такі тести відрізняються від запуску на вашій основній СУБД? Які розбіжності діалектів SQL можливі?

**Для захисту:** Перевіряю реальні запити, CRUD, сортування, сторінки, FK/CHECK/UNIQUE, атомарність транзакцій та batch. In-memory БД ізольована для тесту й не чіпає мої нотатки.

Основна БД у нас **теж H2 тієї самої версії**, але у файловому режимі. In-memory не перевіряє збереження файлу після виходу, тому окремі тести закривають/відкривають файлову БД. Дискові й експлуатаційні властивості не доводяться лише RAM-тестами.

При переході на іншу СУБД відрізнятимуться H2 MERGE KEY, identity/sequence, CLOB/типи, колації, блокування, рівні ізоляції, синтаксис пагінації та тексти помилок. Успішний H2-тест не доводить сумісність з PostgreSQL; потрібні інтеграційні перевірки на цільовій СУБД.
