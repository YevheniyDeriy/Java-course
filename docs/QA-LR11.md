# ЛР №11 — усі 26 відповідей: Hibernate ORM і Jakarta Persistence

[Пояснення проєкту з нуля](DEFENSE.md) · [45 відповідей до Maven/JDBC](QA-LR10.md)

Відповіді прив'язані до нашої реалізації: Hibernate **7.4.14.Final**, Jakarta Persistence **3.2**, окремі ORM-сутності та незмінена схема H2. Слово «сутність» у частині про EntityManager означає `NoteRecord`/`CategoryRecord`, а не незмінний доменний `TextNote`.

## ORM, JPA та Hibernate

### 1. Яку проблему вирішує ORM? Що таке об'єктно-реляційна неузгодженість? Наведіть приклад зі своєї предметної області.

**Для захисту:** ORM відображає об'єкти та їхні зв'язки на таблиці, колонки й ключі. Об'єктно-реляційна неузгодженість — відмінність між об'єктною моделлю Java та реляційною моделлю БД.

Java має об'єкти, посилання, колекції, наслідування; SQL — рядки, значення, FK та JOIN. У нас `note.getCategory()` — посилання на CategoryRecord, а в таблиці notes зберігається лише число category_id. Hibernate перетворює одне представлення на інше. Для списку нотаток категорії Java використовує List, а БД знаходить рядки за FK.

ORM не прибирає БД, SQL, транзакції або необхідність думати про продуктивність. Погане завантаження об'єктів може створити багато SQL-запитів, як у нашому N+1-демо.

**Запам'ятай:** ORM — міст між об'єктами й таблицями.

### 2. Чим JPA відрізняється від Hibernate? Яку роль у цій парі відіграє аналогія з JDBC і драйвером?

**Для захисту:** JPA, сучасна назва Jakarta Persistence, — специфікація API та правил ORM. Hibernate — конкретний провайдер, який ці правила реалізує й додає свої можливості.

Аналогія: JDBC задає Connection/PreparedStatement, драйвер H2 їх реалізує; JPA задає EntityManager/анотації, Hibernate їх реалізує. API JPA імпортується з `jakarta.persistence`, Hibernate-специфічне — з `org.hibernate`.

У нас `@Entity`, `@ManyToOne`, EntityManager — стандартні; `@CourseGeneratedId` через `@IdGeneratorType`, `@JdbcTypeCode`, Statistics та LazyInitializationException — Hibernate-специфічні. Тому перехід на інший JPA-провайдер потребуватиме адаптації цих місць. Hibernate для виконання згенерованого SQL використовує JDBC, а не замінює сам драйвер.

### 3. Що саме з коду ЛР №7 (JDBC) ви перестали писати вручну після переходу на Hibernate?

**Для захисту:** У CRUD ORM-сервісу я більше не складаю INSERT/UPDATE/DELETE, не задаю кожен JDBC-параметр і не читаю ResultSet. Hibernate генерує SQL та переносить колонки в ORM-сутності за mapping-анотаціями.

```java
CategoryRecord category = manager.find(CategoryRecord.class, id);
category.setName("Нова назва");
// Поки category managed, UPDATE підготує Hibernate при flush.
```

Залишилося явно проєктувати транзакції, правила save/delete, зв'язки, JPQL, обсяг завантаження та обмеження. У нашій архітектурі також є NoteMapper між незмінною доменною моделлю й ORM-представленням: ORM прибрав JDBC mapRow, але не цю свідому межу між двома моделями. SQL/схема init.sql не зникли.

## Конфігурація та архітектура

### 4. Для чого потрібен файл persistence.xml і чому він лежить саме в META-INF? Що означає ім'я persistence-unit?

**Для захисту:** Persistence.xml описує persistence-unit: провайдера, керовані класи та налаштування. META-INF/persistence.xml — стандартне місце в classpath, де JPA bootstrap шукає цей опис.

```xml
<persistence-unit name="notes-pu" transaction-type="RESOURCE_LOCAL">
    <provider>org.hibernate.jpa.HibernatePersistenceProvider</provider>
    <!-- CategoryRecord, NoteRecord та налаштування -->
</persistence-unit>
```

Ім'я `notes-pu` повинно збігатися з аргументом `Persistence.createEntityManagerFactory("notes-pu", properties)`. Це логічне ім'я конфігурації, **не назва таблиці чи файлу БД**. У нас DataSource передається програмно з DBConnection, тому реквізити не дублюються в XML. Exclude-unlisted-classes виключає свідомо неправильну демонстраційну сутність з основного запуску.

### 5. Чим EntityManagerFactory відрізняється від EntityManager за часом життя та ресурсомісткістю?

**Для захисту:** Фабрика важка й довгоживуча, створюється один раз для конфігурації. EntityManager — короткоживучий контекст роботи з сутностями; його створюємо на операцію й закриваємо.

| Об'єкт | Призначення | Спільний між потоками |
| --- | --- | --- |
| EntityManagerFactory | mapping, створення EntityManager, інфраструктура провайдера | можна використовувати спільно |
| EntityManager | persistence context, managed-сутності, поточна робота | не слід ділити між потоками |

У JpaUtil Singleton зберігається фабрика. Read та inTransaction щоразу викликають createEntityManager, завершують транзакцію й закривають менеджер. Окремі scoped-фабрики у тестах потрібні для окремих БД; це не фабрика на кожен запит у production. EMF закривається до пулу DataSource.

**Запам'ятай:** EMF — фабрика робочих місць, EM — робоче місце однієї операції.

### 6. Що означають значення none, validate, update, create, create-drop параметра hbm2ddl.auto? Чому в основному проєкті використано validate?

**Для захисту:** Вони визначають дії Hibernate зі схемою. Ми використовуємо validate, бо схема вже створюється init.sql, і Hibernate має перевіряти її, а не переробляти.

| Значення | Сенс |
| --- | --- |
| none | не виконувати автоматичні schema actions |
| validate | перевіряти сумісність mapping і наявної схеми |
| update | намагатися пристосувати схему до mapping; не повноцінна контрольована міграція |
| create | створити схему заново, що може знищити попередні таблиці/дані |
| create-drop | створити схему й видалити її при завершенні фабрики |

Порядок нашого запуску: Hikari → ідемпотентний init.sql → EMF → validate. На порожній БД таблиці створює **наш скрипт**, а не validate. Для еволюції production-схеми потрібні контрольовані міграції, а не довіра до update.

### 7. Що станеться, якщо в сутності змінити довжину @Column чи ім'я поля, а таблицю в БД не змінювати? Чи завжди validate це виявляє?

**Для захисту:** Зміна mapping може зробити його несумісним зі схемою, але validate не перевіряє абсолютно всі деталі DDL. Відсутню колонку він виявляє, а повну перевірку length/constraints не гарантує.

Наше SchemaValidationDemo використовує неправильний `@Column(name="name_typo")`, отримує `missing column [name_typo] in table [notes]` та перевіряє, що правильний mapping після цього працює.

Якщо перейменувати **Java-поле**, але залишити явне `@Column(name="created_on")`, назва SQL-колонки може не змінитися. Потрібно натомість оновити JPQL/mappedBy, які використовують імена Java-атрибутів. Якщо змінити `@Column(name=...)`, це вже інше відображення на БД. Не кажи, що будь-яка зміна довжини гарантовано зупинить старт.

### 8. Навіщо діалект SQL, і чому у сучасному Hibernate його, як правило, не вказують явно?

**Для захисту:** Діалект описує особливості конкретної СУБД: типи, функції, пагінацію, генерацію ключів та інший SQL. Hibernate використовує його при перекладі запитів.

За доступного JDBC-підключення сучасний Hibernate зазвичай визначає діалект із metadata БД. У нас так визначається H2Dialect, тому hibernate.dialect у persistence.xml не заданий. Це не означає, що діалект непотрібний: він просто визначений автоматично. Явне налаштування може знадобитися для спеціального діалекту або сценарію без звичайного доступу до metadata.

## Сутності та відображення

### 9. Які вимоги Hibernate ставить до класу-сутності?

**Для захисту:** У нашому переносимому JPA-стилі це клас з @Entity, ідентифікатором @Id, public/protected конструктором без аргументів і доступними для mapping полями. Для звичайних lazy-proxy клас та потрібні методи не повинні бути final.

```java
@Entity
@Table(name = "categories")
public class CategoryRecord extends BaseEntity {
    protected CategoryRecord() { }
    public CategoryRecord(String name) { super(name); }
}
```

Hibernate має розширення порівняно з мінімальними правилами JPA й інші способи побудови/завантаження, але наша робота прямо виконує вимоги умови: нефінальні сутності, конструктори без параметрів, metadata та ключ.

Наші старі доменні TextNote/ReminderNote незмінні та sealed/final, тому їх не зроблено керованими ORM-сутностями. Для БД додані NoteRecord/CategoryRecord; NoteMapper переносить дані між представленнями.

### 10. Чим відрізняються стратегії генерації ключа IDENTITY, SEQUENCE, UUID, AUTO? Яку ви обрали і чому?

**Для захисту:** IDENTITY отримує значення від identity-колонки при INSERT; SEQUENCE бере номер із послідовності; UUID генерує UUID; AUTO доручає вибір провайдеру відповідно до типу й БД.

| Стратегія | Що врахувати |
| --- | --- |
| IDENTITY | ключ зазвичай стає відомим після INSERT; може обмежувати можливості пакетного INSERT |
| SEQUENCE | потрібна послідовність; можна резервувати значення блоками |
| UUID | не числова послідовність, інший тип/розмір ключа |
| AUTO | фактичний механізм треба перевіряти, а не припускати |

**У нас не обрана стандартна IDENTITY/SEQUENCE.** Щоб не змінити plain BIGINT PK схеми ЛР №10 і зберегти доменні id, застосовано `@GeneratedValue` разом із `@CourseGeneratedId`/CourseIdGenerator. Нульовий ORM-id генерується тим самим Java AtomicLong, уже призначений id допускається. На старті DBConnection читає максимальний id обох таблиць.

Це свідомий компроміс для одного процесу. Для кількох процесів треба генератор на боці БД і міграція схеми. [Hibernate Generator API](https://docs.hibernate.org/orm/7.4/javadocs/org/hibernate/generator/Generator.html).

### 11. Чому @Enumerated(EnumType.STRING) краще за ORDINAL? Яка проблема виникне з ORDINAL?

**Для захисту:** String зберігає ім'я значення enum, ordinal — його позицію. Вставка нового значення всередину enum може зрушити позиції й змінити сенс раніше записаних чисел.

```java
enum NoteType { TEXT, REMINDER, RECURRING }
```

При ORDINAL старе число 1 означає REMINDER. Якщо поставити новий тип перед ним, 1 уже означатиме інше. String зберігає `REMINDER` і не залежить від порядку. Проте **перейменування** REMINDER у коді теж потребуватиме міграції даних.

У NoteRecord стоять `@Enumerated(STRING)` та `@JdbcTypeCode(VARCHAR)`, бо існуючий note_type — VARCHAR(16), а не новий H2 ENUM. Значення збігаються з CHECK у init.sql.

### 12. Для чого параметри nullable, length, precision, scale в @Column? Хто їх використовує, якщо схему створено вашим init.sql?

**Для захисту:** Це metadata колонки: чи дозволено NULL, максимальна довжина рядка, загальна кількість десяткових цифр та кількість цифр після крапки.

```java
@Column(name = "name", nullable = false, length = 255)
private String name;
// Приклад для іншої предметної області:
@Column(precision = 10, scale = 2)
private BigDecimal amount;
```

Провайдер використовує mapping при schema generation, перевірках та роботі зі значеннями. Але при validate існуючі constraints у БД не змінюються. @Column — не заміна окремій валідації введення й не гарантія, що Hibernate перевірить усі DDL-деталі на старті. Фактичні NOT NULL/UNIQUE/CHECK задає init.sql і виконує H2. Грошей у нашій схемі немає, тому precision/scale для них не вигадуємо.

### 13. Що робить анотація @Transient? Наведіть приклад поля з вашого проєкту, яке доречно позначити таким чином.

**Для захисту:** Вона виключає атрибут із персистентного mapping. Похідне значення не треба зберігати окремою колонкою.

Наш `NoteRecord.getWordCount()` обчислює кількість слів із content. Тому для нього не потрібна колонка word_count, яка могла б розійтися з текстом.

**Точна деталь нашого коду:** @Id розташований на полі BaseEntity, тому використовується field access. Обчислюваний getter без backing field і так не був би персистентним полем; @Transient на getter додатково пояснює намір. Для виключення реального поля за field access анотацію потрібно ставити на це поле. Не плутай JPA @Transient з Java `transient`: останній також пов'язаний із серіалізацією Java.

### 14. Що таке @MappedSuperclass і чим він відрізняється від @Entity з наслідуванням? Для чого ви використали його для BaseEntity?

**Для захисту:** MappedSuperclass дає підкласам спільний mapping полів, але сам не є сутністю, окремою таблицею чи коренем поліморфного JPQL-запиту.

`orm.entity.BaseEntity` містить id/name, а їхні колонки знаходяться в кожній конкретній таблиці categories і notes. Запит `from BaseEntity` для цього mapped superclass не є звичайним поліморфним JPA-запитом.

Якщо базовий клас позначити @Entity та задати стратегію наслідування, він стає частиною ієрархії сутностей, для якої можна запитувати поліморфні результати. У нас категорія й нотатка просто мають спільні технічні поля; робити їх однією бізнес-ієрархією не потрібно.

### 15. Назвіть стратегії відображення ієрархії класів (SINGLE_TABLE, JOINED, TABLE_PER_CLASS). У яких випадках яка доречна?

**Для захисту:** Single table — одна таблиця для всієї ієрархії; joined — таблиця базового класу та таблиці підкласів із JOIN за id; table per class — окрема повна таблиця кожного конкретного класу.

| Стратегія | Перевага | Компроміс |
| --- | --- | --- |
| SINGLE_TABLE | прості швидкі поліморфні читання | багато nullable колонок підтипів, discriminator |
| JOINED | нормалізована структура й поля підтипів окремо | додаткові JOIN |
| TABLE_PER_CLASS | кожен конкретний тип має повний рядок | дублювання спільних колонок, UNION для поліморфізму |

У нашій ORM **немає @Inheritance для підтипів нотаток**: одна NoteRecord з enum type, а NoteMapper відновлює TextNote/ReminderNote/RecurringReminderNote. Це табличне зберігання з дискримінатором, подібне за ідеєю до single table, але не слід заявляти, що ми реалізували JPA @Inheritance(SINGLE_TABLE). BaseEntity є @MappedSuperclass.

## Зв'язки та завантаження

### 16. Що таке власник зв'язку (owning side)? Чому в зв'язку «автор — книги» власником є саме @ManyToOne-сторона?

**Для захисту:** Власник — сторона, mapping якої визначає запис зв'язку в БД. У двоспрямованому 1:N FK знаходиться в таблиці «багато», тому ManyToOne-сторона є власником.

У нас це `NoteRecord.category`, відображений на `notes.category_id`. Хоча категорія логічно «містить» нотатки, власником у термінах ORM є нотатка. Це технічне правило зберігання, а не ієрархія важливості бізнес-об'єктів.

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "category_id", nullable = false)
private CategoryRecord category;
```

У БД немає окремої колонки зі списком усіх нотаток у categories: діти знаходяться за своїм FK.

### 17. Що станеться, якщо додати книгу лише до author.getBooks(), не викликавши book.setAuthor(...)? Для чого потрібні допоміжні методи addBook/removeBook?

**Для захисту:** Зворотна колекція в пам'яті зміниться, але owning side може залишитися старою. Hibernate орієнтується на власника, тому FK не буде встановлено так, як ми очікуємо.

У нашому випадку допоміжний метод робить обидві частини узгодженими:

```java
category.addNote(note); // делегує note.setCategory(category)
```

SetCategory прибирає нотатку зі старої колекції, змінює посилання й додає до нової. GetNotes повертає незмінну для зовнішнього коду обгортку, тому додавання йде через helper.

У нас FK обов'язковий: removeNote тимчасово встановлює category=null. До flush треба перепризначити категорію або явно видалити нотатку; сам виклик removeNote не означає DELETE, оскільки orphanRemoval=false.

### 18. Що означає атрибут mappedBy? Яка колонка створюється в БД і в якій таблиці?

**Для захисту:** MappedBy указує **ім'я Java-атрибута власника**, а не назву SQL-колонки. Він позначає зворотну сторону вже описаного зв'язку.

```java
@OneToMany(mappedBy = "category", fetch = FetchType.LAZY)
private List<NoteRecord> notes;
```

Слово category посилається на `NoteRecord.category`. `@JoinColumn(name="category_id")` на цьому полі задає FK у notes. У нашому режимі validate Hibernate колонку не створює: вона вже є в init.sql. MappedBy не вимагає таблиці notes_categories для цього двоспрямованого 1:N.

**Пастка:** `mappedBy="category_id"` було б помилкою, бо такого Java-атрибута у NoteRecord немає.

### 19. Що таке cascade? Які типи ви вказали й чому? Чому REMOVE небезпечний на стороні @ManyToOne?

**Для захисту:** Cascade поширює певну операцію EntityManager з однієї сутності на пов'язані. Це правило ORM, не те саме, що ON DELETE у БД.

У CategoryRecord.notes: **PERSIST і MERGE**. Persist нової категорії з новими нотатками зберігає весь граф; merge переносить стан графа в managed-копії. REMOVE немає, бо видалення категорії не повинно автоматично видаляти дітей; діє FK RESTRICT. На NoteRecord.category каскадів немає.

REMOVE на ManyToOne міг би при видаленні однієї нотатки спробувати видалити спільну категорію, на яку посилаються інші нотатки. Це небажана семантика. ALL включає REMOVE, тому «поставити ALL на все» — необґрунтоване рішення. Інші cascade types — REFRESH і DETACH — також відповідають конкретним операціям життєвого циклу.

### 20. Що робить orphanRemoval = true? Чим воно відрізняється від CascadeType.REMOVE?

**Для захисту:** OrphanRemoval видаляє керованого дочірнього об'єкта, коли його прибрали зі зв'язку з батьком, для якого задана ця семантика. Cascade REMOVE поширює явне видалення батька на дітей.

Приклад для приватних позицій замовлення: видалили позицію з `order.items` — вона більше не потрібна, тож orphanRemoval=true може бути доречним. Видалили саме order — REMOVE може видалити його items.

У нас **orphanRemoval=false**, бо нотатку можна переносити між категоріями й не слід видаляти її лише через вилучення з колекції. Через NOT NULL не можна залишити її без категорії до flush. Жодне з цих ORM-налаштувань не замінює FK та ON DELETE, які виконуються безпосередньо БД.

### 21. Поясніть різницю між LAZY та EAGER. Які значення за замовчуванням має кожен тип зв'язку і чому на практиці рекомендують LAZY?

**Для захисту:** Lazy дозволяє відкласти завантаження зв'язку до потреби; eager вимагає його завантаження разом зі станом сутності за правилами провайдера. Eager не означає обов'язково один JOIN.

Типові JPA defaults для анотацій зв'язків у нашій версії:

| Зв'язок | Default |
| --- | --- |
| ManyToOne | EAGER |
| OneToOne | EAGER |
| OneToMany | LAZY |
| ManyToMany | LAZY |

Lazy для деяких відображень є підказкою провайдеру, а не абсолютною гарантією. У нас обидва зв'язки явно LAZY. Для конкретної операції потрібний граф завантажує JOIN FETCH. Це дозволяє не тягнути всі колекції без потреби, але вимагає планувати доступ до них до закриття EntityManager. Default і семантика mapping визначені [Jakarta Persistence 3.2](https://jakarta.ee/specifications/persistence/3.2/jakarta-persistence-spec-3.2.html).

### 22. Що таке LazyInitializationException? За яких умов вона виникає і чому не слід лікувати її переведенням усього на EAGER?

**Для захисту:** Це Hibernate-виняток, коли потрібно завантажити ще не ініціалізований lazy-зв'язок, але потрібної відкритої сесії/контексту вже немає.

```java
CategoryRecord detached = jpa.read(em -> em.find(CategoryRecord.class, id));
// jpa.read вже закрив EntityManager:
detached.getNotes().size(); // lazy-колекція потребує завантаження
```

Наше демо відтворює це навмисно. Виправлення: отримати потрібні notes у тому самому scope через JOIN FETCH, entity graph, явне завантаження або повернути готовий DTO/доменне значення. Якщо зв'язок уже був завантажений, сам факт закриття EM не забороняє читати ці дані.

Скрізь EAGER може дати надмірний граф, багато SQL і погану продуктивність, а не продуманий fetch plan. Наші звичайні сервіси маплять NoteRecord у доменний Note, поки менеджер відкритий.

### 23. Що таке проблема N+1? Покажіть на своєму прикладі, скільки запитів виконувалося до й після виправлення.

**Для захисту:** Спочатку один запит завантажує N батьків, потім для кожного окремий запит читає дітей. У моєму демо 3 категорії з 6 нотатками: **4 запити до виправлення і 1 після JOIN FETCH**.

```java
// Усередині відкритого EntityManager:
List<CategoryRecord> categories = em.createQuery(
        "select c from CategoryRecord c", CategoryRecord.class).getResultList();
for (CategoryRecord category : categories) {
    category.getNotes().size();
}
```

Формула: 1 запит списку + 3 запити колекцій = 4. У виправленому варіанті `left join fetch c.notes` приносить дітей одразу. Лічильник — `Statistics.getPrepareStatementCount()`, перед кожним способом статистику очищають, новий EntityManager не має прогрітого першого кешу, L2 кеш вимкнено.

Не плутай: N+1 зазвичай виконується **успішно, але дорого**, тоді як lazy-доступ після закриття EM кидає виняток. Фактична кількість може залежати від batch fetching/кешів; у нашому контрольованому демо вона перевіряється як 4 → 1.

### 24. Як працює JOIN FETCH? Які обмеження виникають у разі поєднання його з пагінацією?

**Для захисту:** Join fetch каже завантажити не тільки кореневі сутності, а й пов'язаний атрибут у цьому запиті. Звичайний JOIN може використовуватися лише для умов і сам по собі не означає ініціалізацію зв'язку.

```jpql
select distinct c
from CategoryRecord c
left join fetch c.notes
order by c.id
```

LEFT залишає категорії без дітей. Колекційний JOIN множить SQL-рядки: одна категорія з двома нотатками дає два рядки. Просте LIMIT по них не дорівнює ліміту категорій.

**Відповідь з урахуванням нашої версії:** у старіших Hibernate таку пагінацію часто виконували в пам'яті або забороняли прапорцем fail_on_pagination_over_collection_fetch. У **Hibernate 7.4** для підтримуваних діалектів, включно з H2, провайдер може обмежити батьків у SQL-підзапиті й потім приєднати всіх дітей. Це прямо описано в [Hibernate 7.4 migration guide](https://docs.hibernate.org/orm/7.4/migration-guide/#limits-and-fetch-joins).

У додатковому запуску саме **7.4.14.Final** із нашими налаштуваннями `setMaxResults(1)` повернув **1 категорію, усі 2 нотатки, 1 SQL-запит**. Тому казати, що ця комбінація в нашій версії завжди падає, неправильно. Треба враховувати провайдера/діалект/запит. Переносимий контрольований варіант — спочатку сторінка id батьків, потім fetch за цими id.

У робочому `HibernateNoteService.findPage` JOIN FETCH іде до **однієї категорії**, а не колекції, тому рядки нотаток не множаться. N+1-демо не використовує пагінацію.

### 25. Чому в toString() двоспрямованих сутностей не слід включати обидві сторони зв'язку? До чого це призведе?

**Для захисту:** Категорія містить нотатки, нотатка містить категорію. Якщо toString кожного друкує іншу сторону, виникає рекурсія аж до StackOverflowError.

Додатково друк lazy-поля може зробити прихований SQL-запит, створити N+1 або кинути LazyInitializationException після закриття EM. Тому наші toString друкують лише id/name:

```java
return "CategoryRecord[id=" + getId() + ", name=" + getName() + "]";
```

Це саме міркування стосується автоматично згенерованих equals/hashCode: включення двоспрямованих колекцій може дати рекурсію, завантаження графа та нестабільну рівність. У нас рівність ORM об'єктів спирається на тип і ненульовий id, а hashCode сталий для типу.

### 26. Коли для зв'язку доречний @ManyToMany? Як він відображається в схемі БД

**Для захисту:** Коли багато об'єктів однієї сутності пов'язані з багатьма іншої. Наприклад, нотатка має кілька тегів, і тег належить багатьом нотаткам.

```text
notes(id, ...)
tags(id, name)
note_tags(note_id FK, tag_id FK, PRIMARY KEY(note_id, tag_id))
```

Потрібна таблиця зв'язку, яку описують JoinTable/JoinColumn; двоспрямований ManyToMany має власника та mappedBy з іншого боку. Саме пара ключів у join table представляє зв'язок. Для спільних тегів cascade REMOVE зазвичай небезпечний.

Якщо зв'язок має власні дані, наприклад assignedAt, author або weight, краще зробити окрему сутність NoteTag з двома ManyToOne. У поточній лабораторній ManyToMany **не реалізований**: категорія одна для кожної нотатки, тому достатньо 1:N.
